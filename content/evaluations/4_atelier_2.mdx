# Atelier 2 : un clavardage dans Quiz M9

- **Pondération** : 5 %
- **Modalité** : individuel, en classe, pendant le bloc de l'atelier de la
  semaine 9
- **Documentation** : toute documentation permise, y compris
  les notes de cours et la documentation de Socket.IO ([accusés de réception](https://socket.io/docs/v4/emitting-events/#acknowledgements)
et les [salons](https://socket.io/docs/v4/rooms/)).

## Ce qu'on construit

Chaque partie a son propre clavardage. Il commence dans le salon d'attente
et se poursuit dans la salle de jeu. Les joueurs y écrivent des messages.
L'animateur les lit et peut désactiver ou réactiver le clavardage à tout
moment.

Les événements Socket.IO :

| Sens | Événement | Signification |
|---|---|---|
| navigateur → serveur | `'join', code, ack` | Existe déjà. Le serveur répond maintenant `ack({ game, chat })`, où `chat` est l'objet `{ enabled, messages }`. |
| navigateur → serveur | `'chat:send', { nickname, text }, ack` | Le joueur envoie un message. Le serveur répond `ack({})` s'il l'accepte, `ack({ error })` s'il le refuse. |
| serveur → navigateur | `'chat:message', { id, nickname, text, sentAt }` | Le serveur diffuse un nouveau message à tout le salon. |
| serveur → navigateur | `'chat:enabled', enabled` | Le serveur annonce que l'animateur a désactivé (`false`) ou réactivé (`true`) le clavardage. |

L'animateur active ou désactive le clavardage par une requête HTTP :

| Route | Corps | Réponse |
|---|---|---|
| `POST /api/games/:code/chat` | `{ enabled }` | `200 { enabled }` en cas de succès ; sinon 400, 401, 403 ou 404 |

Le serveur conserve le clavardage **en mémoire**, dans `realtime.js`. La
base de données ne change pas.

### Le serveur

1. En haut de `realtime.js`, sous `let io = null;`, déclarez une `Map` qui
   associe le code de chaque partie à son clavardage,
   `{ enabled, messages }`.

   ```js
   /** Le chat de chaque partie, en mémoire : code → { enabled, messages }. */
   const chats = new Map();
   let nextMessageId = 1;

   /** Retourne le chat de cette partie. Le crée, actif et vide, au premier appel. */
   function chatOf(code) {
     // À vous : si chats ne contient pas encore ce code,
     // associez-lui { enabled: true, messages: [] } avec chats.set.

     return chats.get(code);
   }
   ```

2. Dans le gestionnaire de `'join'`, juste après `socket.join(game.code)`,
   enregistrez le code de la partie dans `socket.data`. Socket.IO fournit
   cet objet, vide au départ, à chaque connexion : on y stocke ce qu'on
   veut retrouver plus tard pour cette connexion.

   ```js
   socket.join(game.code);
   socket.data.code = game.code; // 'chat:send' lira ici la partie de CETTE connexion
   ```

3. Ajoutez le gestionnaire de `'chat:send'` dans
   `io.on('connection', ...)`, à côté de celui de `'join'`. Il suit la même
   structure.

   ```js
   socket.on('chat:send', async (message, ack) => {
     if (typeof ack !== 'function') return;

     try {
       // À vous
     } catch (err) {
       console.error(err);
       ack({ error: 'Erreur du serveur.' });
     }
   });
   ```

   `message` vient du navigateur : rien ne garantit sa forme, ni même que
   c'est un objet. Dans le `try`, écrivez les étapes suivantes, dans cet
   ordre :

   1. **La partie.** Lisez le code de la partie dans `socket.data.code`,
      que le gestionnaire de `'join'` a enregistré à l'étape 2. S'il est
      absent, la connexion n'a rejoint aucune partie : répondez
      `ack({ error: 'Suivez d’abord une partie.' })`.
   2. **Le texte.** Si `message?.text` est une chaîne, retirez les espaces
      à ses extrémités avec `trim()` ; sinon, utilisez la chaîne vide `''`.
      Si le texte obtenu est vide ou dépasse 200 caractères, répondez
      `ack({ error })` avec un message de votre choix.
   3. **Le joueur.** Cherchez la partie avec
      `repository.findGameByCode(code)`, puis le joueur avec
      `repository.findPlayer(game.id, message?.nickname)`. Si **cette**
      partie n'a aucun joueur de ce pseudonyme, répondez `ack({ error })`.
   4. **Le message.** Construisez l'objet `{ id, nickname, text, sentAt }`.
      Obtenez `id` avec `nextMessageId++` : React s'en servira comme `key`.
      Donnez à `sentAt` la valeur `Date.now()`.
   5. **Conserver, diffuser, répondre.** Ajoutez le message à la fin de
      `chatOf(code).messages`, diffusez-le sous le nom `'chat:message'`
      avec `io.to(code).emit(...)`, puis répondez `ack({})`.

   `io.to(code)` envoie à tout le salon, **expéditeur compris**.
   `socket.to(code)` exclurait l'expéditeur, et son propre message
   n'apparaîtrait jamais à son écran : le client n'affiche que les messages
   reçus par `'chat:message'`.

   Aux étapes 1 à 3, écrivez chaque réponse d'erreur sous la forme
   `return ack({ error })`, comme dans le gestionnaire de `'join'`. Appeler
   `ack` envoie la réponse, mais n'arrête pas la fonction : sans `return`,
   l'exécution passe à l'étape suivante et pourrait, par exemple, diffuser
   un message invalide.

   À l'inverse, chaque chemin du gestionnaire doit appeler `ack`. Le
   navigateur attend la réponse avec `emitWithAck`, sans délai maximal :
   si elle ne vient jamais, sa promesse ne se résout jamais et
   `sendMessage` reste bloquée.

### Le client

1. Dans `client/app/useGame.js`, `useGame(code)` retourne maintenant
   `{ game, chat, sendMessage }` au lieu de `game` seul. Le squelette
   montre les ajouts ; le reste du fichier ne change pas.

   ```js
   import { useEffect, useRef, useState } from 'react';
   // …

   export function useGame(code) {
     const [game, setGame] = useState(null);
     const [chat, setChat] = useState({ enabled: true, messages: [] }); // Ajout 1
     const socketRef = useRef(null); // Ajout 2

     useEffect(() => {
       if (!code) return;

       const socket = io({ transports: ['websocket'] });
       socketRef.current = socket; // Ajout 2

       // … les gestionnaires de 'connect' et 'state', inchangés

       // Ajout 3
       socket.on('chat:message', (message) => {
         // À vous : appelez setChat((chat) => ({ ...chat, messages: ... }))
         // en ajoutant message à la fin de chat.messages.
       });

       return () => {
         socket.disconnect();
       };
     }, [code]);

     // Ajout 4
     /** Envoie un message au chat. Retourne une promesse de la réponse, {} ou { error }. */
     function sendMessage(nickname, text) {
       // À vous : émettez 'chat:send' avec { nickname, text } sur socketRef.current,
       // avec emitWithAck, et retournez sa promesse.
     }

     return { game, chat, sendMessage };
   }
   ```

   Les ajouts, dans l'ordre :

   1. **L'état `chat`.** Un deuxième `useState` tient le clavardage,
      `{ enabled, messages }`. Il commence activé et vide.
   2. **La référence `socketRef`.** `sendMessage` est définie hors du
      `useEffect` : elle ne voit pas la variable locale `socket`.
      `useRef(null)` crée une boîte, `socketRef.current`, que React
      conserve d'un rendu à l'autre. Le `useEffect` y range la connexion,
      `sendMessage` l'y retrouve. Contrairement à un état, modifier
      `socketRef.current` ne provoque pas de nouveau rendu.
   3. **Recevoir.** Complétez le gestionnaire de `'chat:message'` : il
      ajoute `message` à la fin de `chat.messages`.
   4. **Envoyer.** Complétez `sendMessage`. `emitWithAck` est la version
      promesse de `emit` avec un ack : au lieu de passer une fonction de
      rappel, on reçoit une promesse qui se résout avec la réponse du
      serveur, `{}` ou `{ error }`. La fonction `join` de
      `server/test/realtime.test.js` s'en sert déjà.

   **Pourquoi `setChat((chat) => ...)` et non `setChat({ ...chat, ... })` ?**
   Rappel : quand on passe une fonction à `setChat`, React l'appelle avec
   l'état **actuel** en paramètre et en fait le nouvel état avec la valeur de
   retour.

   Sans fonction, on lirait la variable `chat` du composant. Or le
   gestionnaire de `'chat:message'` est créé une seule fois, quand le
   `useEffect` s'exécute. La variable `chat` qu'il voit est celle de ce
   rendu, où la liste est vide, et elle ne change jamais pour lui. Avec
   `setChat({ ...chat, ... })`, chaque nouveau message s'ajouterait à cette liste
   vide et donc remplacerait uniquement le précédent.

## En panne ?

- Le `chat:send` part (onglet Messages), mais aucun `chat:message`
  n'arrive : le serveur émet sur `socket` au lieu de `io.to(code)`, ou le
  gestionnaire de `'join'` n'enregistre pas `socket.data.code`.
- La promesse de `sendMessage` ne se résout jamais : une branche de
  `'chat:send'` n'appelle pas `ack`.
- Les messages apparaissent en double : `Chat` ajoute lui-même le message
  à la liste, en plus de `'chat:message'`, ou `useGame` ajoute le `chat` du
  `join` à l'état au lieu de le remplacer.
- Seul le dernier message reste affiché : `setChat({ ...chat, ... })` lit
  un `chat` périmé. Utilisez la forme fonction, `setChat((chat) => ...)`.
- `Cannot read properties of null (reading 'emitWithAck')` : `useGame`
  n'a pas enregistré la connexion dans `socketRef.current`.
- La salle de jeu affiche « Chargement… » pour toujours, ou plante sur
  `game.state` : `game.jsx` contient encore `const game = useGame(code)`.
- Un clic sur le bouton de l'animateur affiche « Connectez-vous. » ou
  « Seul l’animateur fait avancer la partie. » : cet onglet n'est pas
  connecté avec le compte qui a lancé la partie.
- React affiche l'avertissement `unique "key" prop` : donnez à chaque
  `<li>` la `key` `m.id`.
- `npm test` ne se termine pas : une connexion reste ouverte. Appelez
  `socket.disconnect()` à la fin de chaque test.
