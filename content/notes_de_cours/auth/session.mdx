# La session

Le flux [OAuth 2](oauth) se termine sur un profil et une redirection :

```json
{ "id": 583231, "login": "octocat", "name": "The Octocat", "avatar_url": "https://…" }
```

GitHub nous a laissé établir qui est devant le navigateur. **Une fois.** La requête
suivante, celle de `/quizzes`, arrivera nue : ni code, ni jeton, ni profil.
HTTP n'a pas de mémoire. Retenir cette identité d'une requête à l'autre,
c'est le rôle de la session.

Dans Quiz M9, **la session est un jeton signé, transporté par un cookie que
l'API pose elle-même** :

```
quizm9_session=<{ accountId, exp } en base64url>.<signature HMAC>
```

## Du profil GitHub au compte

Qu'est-ce qu'on garde du profil ? **Un identifiant stable.** Le
nom, l'avatar et le courriel changent ; le champ `id`, un entier attribué
par GitHub, ne change jamais.

D'où la table `account` (`server/data/schema.sql`) :

```sql
CREATE TABLE IF NOT EXISTS account (
  id         INTEGER PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
  github_id  BIGINT NOT NULL UNIQUE,
  login      TEXT NOT NULL,
  name       TEXT,
  avatar_url TEXT
);
```

`github_id` est unique : deux connexions du même utilisateur retombent sur
la même ligne. `findOrCreateAccount` (`server/src/repository/accounts.js`)
crée ou retrouve d'un seul coup :

```sql
INSERT INTO account (github_id, login, name, avatar_url)
VALUES ($1, $2, $3, $4)
ON CONFLICT (github_id) DO UPDATE
  SET login = EXCLUDED.login, name = EXCLUDED.name, avatar_url = EXCLUDED.avatar_url
RETURNING *
```

**Il n'y a pas d'inscription** : la première connexion crée le compte. Et
**le profil est rafraîchi à chaque fois** : GitHub est la source de vérité
pour le login et l'avatar, pas nous.

Le `RETURNING *` donne `account.id`, notre clé à nous. C'est elle que
`quiz.account_id` référence et elle qui ira dans la session, pas le
`github_id` : le jour où on ajoute Google, un compte n'est plus une identité
GitHub, mais une identité de Quiz M9 à laquelle des identités externes sont
rattachées.

## Le cookie

Un cookie, c'est une paire nom/valeur que le serveur pose dans une réponse
et que le navigateur **renvoie tout seul** dans chaque requête suivante vers
le même domaine.

```http
← HTTP/1.1 302 Found
  Location: /quizzes
  Set-Cookie: quizm9_session=eyJhY2NvdW50SWQiOjEsImV4cCI6…; HttpOnly; SameSite=Lax; Max-Age=604800; Path=/

→ GET /quizzes HTTP/1.1
  Cookie: quizm9_session=eyJhY2NvdW50SWQiOjEsImV4cCI6…
```

C'est ce « tout seul » qui rend la mémoire à HTTP, sans une ligne de
JavaScript de notre part. Même la toute première requête, celle qui demande
le document HTML quand on tape `/quizzes` dans la barre d'adresse, porte le
cookie : le `loader` sait qui est connecté avant d'avoir rendu quoi que ce
soit.

`writeSession` (`server/src/session.js`) le pose avec quatre attributs importants :

| Attribut | Ce qu'il change | Dans Quiz M9 |
|---|---|---|
| `HttpOnly` | invisible à `document.cookie`, donc un XSS ne le vole pas | oui |
| `SameSite` | quand le cookie part depuis un autre site | `Lax` |
| `Path` | le préfixe d'URL qui le reçoit | `/`, toutes les routes |
| `Max-Age` | quand le navigateur l'oublie | une semaine |
| `Secure` | envoyé seulement en HTTPS | absent en dev, obligatoire en production |

`SameSite=Lax` veut dire : le cookie accompagne une navigation de premier
niveau en `GET` (un lien cliqué depuis un autre site), mais pas un
formulaire ou un `fetch` posté depuis un autre site. C'est la défense de
base contre le **CSRF** (*cross-site request forgery*), où un site piégé
déclenche une requête vers Quiz M9 dans un navigateur déjà connecté.

Attention à `Max-Age` : c'est une consigne donnée au **navigateur**, et le
navigateur est chez l'utilisateur. Rien n'empêche de recopier la valeur du
cookie avant la date et de la rejouer après. La véritable expiration est
celle qui est à l'intérieur du jeton, signée, et que le serveur vérifie
lui-même. `Max-Age` fait le ménage, `exp` fait la sécurité.

## Signer, pas chiffrer

Le cookie est rangé dans un endroit que l'utilisateur contrôle entièrement.
S'il contenait `{"accountId":1,"exp":…}` en clair, il suffirait d'écrire `2`
à la place de `1` pour devenir quelqu'un d'autre. Quiz M9 le **signe** :

```
quizm9_session=<JSON en base64url>.<HMAC-SHA256 de cette chaîne>
```

Le base64url est un encodage, pas un chiffrement : n'importe qui relit le
contenu. La signature, elle, est un HMAC calculé avec `SESSION_SECRET`.
Changez un caractère du contenu et la signature attendue n'est plus la
même : `verifySession` renvoie `{}`, et la requête est simplement anonyme.

Trois conséquences :

**Tout dans le cookie est public.** Jamais mettre le jeton GitHub, de mot de passe ou de donnée privée
dans une session. Signé ne veut pas dire caché.

**`SESSION_SECRET` est le seul verrou.** Qui l'obtient fabrique une session
valide pour n'importe quel `accountId`, sans mot de passe et sans GitHub. Il
vit dans `server/.env`, jamais dans le dépôt. Le changer invalide toutes les
signatures émises, donc déconnecte tout le monde d'un coup.

**La comparaison se fait en temps constant.** `timingSafeEqual` plutôt que
`===` : une comparaison ordinaire s'arrête au premier caractère qui diffère,
et le temps qu'elle met trahit jusqu'où on avait juste.

## Ce qu'on met dedans

`{ accountId, exp }`. Rien d'autre. `accountId` répond à « qui », `exp` à
« jusqu'à quand » :

```js
const DUREE_MS = 7 * 24 * 60 * 60 * 1000; // une semaine

export function signSession(session) {
  const contenu = { ...session, exp: Date.now() + DUREE_MS };
  // …
}
```

`signSession` ajoute `exp` lui-même : impossible d'émettre par distraction
un jeton valable pour toujours. À la relecture, `verifySession` vérifie la
signature **puis** la date, et une session périmée redevient `{}`, comme une
session absente.

La tentation est d'ajouter le login et l'avatar, pour éviter un aller-retour
à la base. Mauvaise idée : ces champs changent, le cookie ne changerait pas,
et l'utilisateur qui se renomme verrait l'ancien nom jusqu'à sa prochaine
connexion. Pire avec un rôle ou un droit : les retirer ne doit pas dépendre
du moment où l'utilisateur voudra bien se reconnecter.

> Dans le cookie, l'identité. Dans la base, tout ce qui peut changer.

C'est pour ça que le client, pour afficher le login et l'avatar en haut de
chaque page, appelle `GET /api/me` plutôt que de lire le cookie : la réponse
vient de la base, à jour. Le prix est un `SELECT` par requête, sur une clé
primaire.

## Le même cookie pour le `state`

Pendant le flux OAuth, il n'y a encore personne à retenir, et pourtant il
faut se souvenir d'une chose entre le départ et le retour : le `state`.
`server/src/auth.js` réutilise le même mécanisme.

```js
// étape 1, avant de partir chez GitHub
writeSession(res, { state });

// étape 4, une fois le profil obtenu
writeSession(res, { accountId: account.id });
```

Le deuxième appel remplace le premier : le `state` disparaît du cookie, ce
qui lui donne son usage unique gratuitement.

## Ce que le jeton signé coûte : la révocation

Le serveur ne garde rien. Il ne sait donc pas quelles sessions existent et
**ne peut pas en supprimer une**. `clearSession` efface le cookie **du
navigateur qui le demande** ; une copie prise avant reste valide. « Se
déconnecter de tous les appareils » est impossible tel quel.

Quiz M9 s'en tient à la parade la moins chère, `exp` : la fenêtre se referme
d'elle-même au bout d'une semaine. Un cran plus haut, une colonne
`session_version` recopiée dans le jeton et comparée à chaque requête
suffirait à invalider d'un coup toutes les sessions d'un compte ; un vrai
registre des sessions donnerait la révocation exacte, au prix d'un registre
à tenir.

Une semaine, c'est un arbitrage sans bonne réponse : une heure et on se
reconnecte sans arrêt, un mois et un cookie volé sert un mois. Dans une
application plus sérieuse que Quiz M9, la question « comment je déconnecte
quelqu'un de force ? » se pose avant d'écrire la première ligne.

## Où vit la session

Dans l'**API**, pas dans React Router. Une requête sans cookie valide est
anonyme, d'où qu'elle vienne : d'un `loader`, du navigateur, ou de `curl`.

```bash
curl -i -X POST http://localhost:3000/api/quizzes \
  -H "content-type: application/json" -d '{"title":"Pirate"}'
```

`401`. Le client peut cacher un bouton, ça n'empêche personne d'appeler la
route : **l'autorisation se décide là où sont les données**. Une seule
fonction fait le pont entre le cookie et le compte, et toute route protégée
commence par elle :

```js
export async function currentAccount(req) {
  const { accountId } = readSession(req);
  if (!accountId) return null;
  return (await repository.findAccount(accountId)) ?? null;
}
```

## Le cookie voyage

Le navigateur ne parle qu'au client (5173), qui relaie `/api` vers l'API
(3000). Mais une même requête peut suivre deux chemins :

```
navigateur ──► client 5173 ──(relais /api)────► API 3000    un fetch du navigateur
navigateur ──► client 5173 ──(loader/action)──► API 3000    le rendu côté serveur
```

**Premier chemin.** Le navigateur joint le cookie lui-même. Le relais de
Vite transmet `Cookie` et `Set-Cookie` ; en production, `client/server.js`
le fait explicitement.

**Deuxième chemin.** Un `loader` ou une `action` tourne dans Node. Son
`fetch` part d'un processus qui n'est pas un navigateur et n'a donc aucun
cookie : il faut recopier celui de la requête entrante, ce que fait
`apiFetch` (`client/app/api-url.js`) :

```js
export function apiFetch(request, path, init = {}) {
  const headers = { ...init.headers, cookie: request.headers.get('cookie') ?? '' };
  return fetch(`${API_URL}${path}`, { ...init, headers });
}
```

Le retour se recopie aussi : à la déconnexion, le `Set-Cookie` d'effacement
arrive dans la réponse adressée au serveur du client, et l'`action` doit le
replacer dans la sienne pour qu'il atteigne le navigateur.
