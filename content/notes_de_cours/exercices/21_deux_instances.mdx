# Exercice 20 : deux instances

:::info

Ceci est un exercice formatif. Il n'y a rien à remettre. Il demande
**Docker Desktop**, démarré, et le dossier `deploy/` de
l'[exercice 18](/notes_de_cours/exercices/deploiement) (jalons 1 et 2).

:::

Quiz M9 tourne en un seul exemplaire. Cette semaine, on en démarre deux
derrière Caddy, on regarde ce qui casse, puis on répare.

Tout se passe sur votre poste, dans la « prod » de `deploy/`.

| Jalon | Ce que vous faites | Pourquoi |
|---|---|---|
| 0 | récupérer la semaine, mesurer avec une instance | avoir un point de comparaison |
| 1 | deux instances de l'API derrière Caddy | voir ce que l'API garde en mémoire |
| 2 | l'adaptateur Redis | relier les connexions des deux instances |
| 3 | le chat dans la base | sortir le dernier état de la mémoire |
| 4 | arrêter une instance en pleine partie | vérifier que plus rien d'important n'y vit |

Note à garder ouverte :
[La montée en charge](/notes_de_cours/architecture/montee_en_charge).

## Jalon 0 : récupérer la semaine

Le point de départ est la solution de la semaine 12.

```bash
git checkout main
git pull
git checkout -b sem-13
npm install
```

Trois choses sont fournies : les paquets Redis (déjà dans
`server/package.json`), `server/src/redis.js` et les robots de
`attacks/salon.js`.

### Les images

Comme à l'[exercice 19](/notes_de_cours/exercices/migrations), la prod de
`deploy/` fait tourner des images, construites sur le poste. Cette semaine,
un seul tag : `s13`.

1. À la racine du dépôt :

   ```bash
   docker build -f server/Dockerfile -t ghcr.io/archambaultv/quizm9-api:s13 .
   docker build -f client/Dockerfile -t ghcr.io/archambaultv/quizm9-client:s13 .
   ```

2. Dans `deploy/.env`, mettez `TAG=s13`.

3. Dans `deploy/` :

   ```bash
   docker compose down -v
   docker compose up -d
   ```

:::note[Après chaque changement au code du serveur]

Dans cet exercice, « **reconstruisez** » veut dire : à la racine du dépôt,

```bash
docker build -f server/Dockerfile -t ghcr.io/archambaultv/quizm9-api:s13 .
```

puis, dans `deploy/`, `docker compose up -d`. Compose remplace les
conteneurs dont l'image a changé (`Recreated`). L'image du client ne change
pas de l'exercice.

:::

### La mesure

1. Sur `https://quizm9.localhost`, connectez-vous (`alice` / `alice`) et
   créez une partie. Restez dans le salon d'attente.
2. À la racine du dépôt, avec le code de la partie :

   ```bash
   node attacks/salon.js 747311
   ```

Six robots rejoignent la partie, ouvrent chacun une connexion Socket.IO,
puis le script compte ce que chacun reçoit :

```
1. Un joueur rejoint. États reçus par chaque robot : 1 1 1 1 1 1   (attendu : 1 partout)
2. Joueurs en ligne, vus par chaque robot : 6 6 6 6 6 6   (attendu : 6 partout)
3. Deux messages envoyés. Reçus par chaque robot : 2 2 2 2 2 2   (attendu : 2 partout)
   Id des messages : 1 2   (attendu : deux id différents)
4. Deux spectateurs arrivent. Messages dans leur historique : 2 2   (attendu : 2 2)
```

Avec une seule instance, tout est conforme. C'est la mesure qu'on refera à
chaque jalon, sur une partie **neuve** chaque fois.

## Jalon 1 : deux instances

- **Fichiers** : `deploy/compose.yml`, `deploy/Caddyfile`
- **Note** : [Le répartiteur de charge](/notes_de_cours/architecture/montee_en_charge#le-répartiteur-de-charge)

1. **Deux instances.** Dans `deploy/compose.yml`, service `api`, ajoutez
   sous `image:` :

   ```yaml
       deploy:
         replicas: 2
   ```

2. **La répartition.** Dans `deploy/Caddyfile`, remplacez le bloc du site
   par :

   ```caddy title="deploy/Caddyfile"
   (instances) {
   	dynamic a {args[0]} 3000 {
   		refresh 2s
   	}
   	lb_policy round_robin
   	lb_try_duration 3s
   }

   {$DOMAIN} {
   	reverse_proxy /api/* {
   		import instances api
   	}
   	reverse_proxy /socket.io/* {
   		import instances api
   	}
   	reverse_proxy client:5173
   }
   ```

   `(instances)` est un bloc réutilisable : `import instances api` le
   recopie, avec `{args[0]}` remplacé par `api`. Le tableau de la note
   explique chaque ligne.

3. Dans `deploy/` :

   ```bash
   docker compose up -d
   docker compose restart caddy
   docker compose ps
   ```

   `restart caddy` : Caddy ne relit son `Caddyfile` qu'au démarrage.
   `docker compose ps` montre `deploy-api-1` et `deploy-api-2`.

**Prédire.** Avant de mesurer, remplissez la troisième colonne du
[tableau de l'inventaire](/notes_de_cours/architecture/montee_en_charge#un-service-sans-état)
sans la regarder : pour chaque état, que se passera-t-il avec deux
instances ?

**Observer.**

1. Créez une partie neuve, puis `node attacks/salon.js <code>`. Notez les
   quatre lignes.
2. Dans le navigateur : créez une partie, et rejoignez-la dans trois autres
   onglets (trois pseudonymes). Écrivez dans le chat. Lancez la première
   question. Qui voit quoi ?
3. Dans un onglet resté dans le salon d'attente, rechargez la page.

**Expliquer.**

- Pourquoi exactement la moitié des robots ?
- Après le rechargement, l'onglet affiche la question. D'où vient-elle,
  puisque personne ne l'a prévenu ?
- Deux messages différents portent le même id. Pourquoi ?

<details>
<summary>Réponses</summary>

- Caddy alterne : trois connexions par instance. `io.to(code).emit(...)`
  n'atteint que les connexions de l'instance qui reçoit la requête HTTP.
- De la base. Le `join` relit l'état complet de la partie. Les **données**
  sont justes sur les deux instances. Ce qui manque, c'est la
  **notification**.
- Chaque instance a sa propre variable `nextMessageId`, qui part de 1.

</details>

## Jalon 2 : l'adaptateur Redis

- **Fichiers** : `deploy/compose.yml`, `server/src/realtime.js`,
  `server/src/server.js`
- **Note** : [L'adaptateur Redis](/notes_de_cours/architecture/montee_en_charge#ladaptateur-redis)

1. **Le service `redis`.** Dans `deploy/compose.yml`, ajoutez-le avant
   `api:` :

   ```yaml
     redis:
       image: redis:8
   ```

   Pas de volume : Redis ne sert ici qu'à faire passer des messages. Pas
   de `ports:` : comme `postgres`, il ne parle qu'au réseau privé.

   Dans le service `api`, ajoutez la variable et la dépendance :

   ```yaml
       environment:
         # …
         REDIS_URL: redis://redis:6379
       depends_on:
         postgres:
           condition: service_healthy
         redis:
           condition: service_started
   ```

2. **L'adaptateur.** Dans `server/src/realtime.js`, deux imports :

   ```js
   import { createAdapter } from '@socket.io/redis-adapter';
   import { REDIS_URL, connectRedis } from './redis.js';
   ```

   Puis, dans `attachRealtime`, qui devient `async` :

   ```js
   export async function attachRealtime(server) {
     io = new Server(server);

     if (REDIS_URL) {
       const [pub, sub] = await Promise.all([connectRedis(), connectRedis()]);
       io.adapter(createAdapter(pub, sub));
     }
     // … la suite ne change pas
   ```

   Sans `REDIS_URL` (`npm run dev`, les tests), Socket.IO garde son
   adaptateur en mémoire : rien ne change pour une instance seule.

3. **Attendre.** Dans `server/src/server.js`, la dernière ligne devient
   `await attachRealtime(server);`.

4. **Le raccourci.** Dans `broadcastState`, la première ligne vérifie que
   quelqu'un suit la partie avant de lire la base :

   ```js
   if (!io?.sockets.adapter.rooms.has(code)) return;
   ```

   **Prédire.** Que se passe-t-il si on la laisse, quand l'animateur est
   sur l'instance 1 et tous les joueurs sur l'instance 2 ?

   Remplacez-la par :

   ```js
   if (!io) return;
   ```

5. `npm test`, puis reconstruisez.

**Vérifier.** Sur une partie neuve, `node attacks/salon.js <code>` :

- les lignes 1 et 2 sont conformes : la diffusion et la présence passent
  d'une instance à l'autre ;
- les lignes 3 et 4 ne le sont pas encore. Les messages arrivent à tout le
  monde, mais les id se répètent et chaque instance a son historique.

**Expliquer.** L'adaptateur a réparé `io.to(...)` et `fetchSockets()`.
Pourquoi pas l'historique du chat ?

<details>
<summary>Réponse</summary>

L'adaptateur relie les **connexions**. La variable `chats` est une `Map`
ordinaire dans la mémoire de chaque instance : Socket.IO ne la connaît
pas.

</details>

## Jalon 3 : le chat dans la base

- **Fichiers** : `server/data/migrations/003_chat_en_base.sql` (nouveau),
  `server/data/schema.sqlite.sql`, `server/src/repository/chat.js`
  (nouveau), `server/src/repository/index.js`, `server/src/realtime.js`,
  `server/src/app.js`
- **Note** : [Où mettre l'état](/notes_de_cours/architecture/montee_en_charge#où-mettre-létat)

Le chat a deux états en mémoire : les messages, et « l'animateur l'a
coupé ». Les deux vont dans la base.

1. **La migration.** Créez `server/data/migrations/003_chat_en_base.sql` :

   ```sql
   ALTER TABLE game ADD COLUMN IF NOT EXISTS chat_enabled BOOLEAN NOT NULL DEFAULT TRUE;

   CREATE TABLE IF NOT EXISTS chat_message (
     id       INTEGER PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
     game_id  INTEGER NOT NULL REFERENCES game(id),
     nickname TEXT NOT NULL,
     text     TEXT NOT NULL,
     sent_at  BIGINT NOT NULL
   );
   CREATE INDEX IF NOT EXISTS chat_message_game ON chat_message (game_id, id);
   ```

   Dans `server/data/schema.sqlite.sql`, le schéma de ceux qui travaillent
   sans Docker : ajoutez `chat_enabled INTEGER NOT NULL DEFAULT 1` à la
   table `game`, et la table `chat_message` (`id INTEGER PRIMARY KEY`,
   `sent_at INTEGER`).

2. **Le dépôt de données.** Créez `server/src/repository/chat.js` :

   ```js
   import { pool } from './db.js';

   /** Enregistre un message et le retourne, tel qu'envoyé aux navigateurs. */
   export async function addChatMessage(gameId, nickname, text, sentAt) {
     const { rows } = await pool.query(
       'INSERT INTO chat_message (game_id, nickname, text, sent_at) VALUES ($1, $2, $3, $4) RETURNING id',
       [gameId, nickname, text, sentAt],
     );
     return { id: rows[0].id, nickname, text, sentAt };
   }

   /** Les `limit` derniers messages d'une partie, du plus ancien au plus récent. */
   export async function getChatMessages(gameId, limit) {
     const { rows } = await pool.query(
       `SELECT id, nickname, text, sent_at
          FROM (SELECT * FROM chat_message WHERE game_id = $1 ORDER BY id DESC LIMIT $2) AS recent
         ORDER BY id`,
       [gameId, limit],
     );
     return rows.map((r) => ({ id: r.id, nickname: r.nickname, text: r.text, sentAt: r.sent_at }));
   }

   /** L'animateur coupe (false) ou rouvre (true) le chat de sa partie. */
   export async function setChatEnabled(gameId, enabled) {
     await pool.query('UPDATE game SET chat_enabled = $1 WHERE id = $2', [enabled, gameId]);
   }
   ```

   Dans `server/src/repository/index.js`, exportez les trois fonctions :

   ```js
   export { addChatMessage, getChatMessages, setChatEnabled } from './chat.js';
   ```

3. **Le temps réel.** Dans `server/src/realtime.js` :

   - supprimez `chats`, `nextMessageId` et l'ancienne fonction `chatOf`.
     La nouvelle relit la base :

     ```js
     async function chatOf(game) {
       return {
         enabled: Boolean(game.chat_enabled),
         messages: await repository.getChatMessages(game.id, MAX_MESSAGES),
       };
     }
     ```

   - dans `'join'`, la réponse devient
     `ack({ game: state, chat: await chatOf(game) });`

   - `'chat:send'` devient `async`. Tout ce qui suit la validation du
     texte est remplacé par :

     ```js
     try {
       const game = await repository.findGameByCode(code);
       if (!game.chat_enabled) {
         return ack({ error: 'Le chat est désactivé.' });
       }
       const entry = await repository.addChatMessage(game.id, player.nickname, text, Date.now());
       io.to(code).emit('chat:message', entry);
       ack({});
     } catch (err) {
       console.error(err);
       ack({ error: 'Erreur du serveur.' });
     }
     ```

   - `setChatEnabled` ne retient plus rien. Renommez-la
     `broadcastChatEnabled` et ne gardez que la ligne qui prévient le
     salon :

     ```js
     export function broadcastChatEnabled(code, enabled) {
       io?.to(code).emit('chat:enabled', enabled);
     }
     ```

4. **La route.** Dans `server/src/app.js`, importez `broadcastChatEnabled`
   à la place de `setChatEnabled`. La route `POST /api/games/:code/chat`
   devient `async` et écrit dans la base avant de prévenir :

   ```js
   await repository.setChatEnabled(req.game.id, enabled);
   broadcastChatEnabled(req.game.code, enabled);
   ```

5. `npm test`, puis reconstruisez.

**Vérifier.**

- La migration a été appliquée **une seule fois**, alors que deux instances
  ont démarré en même temps :

  ```bash
  docker compose logs api
  ```

  C'est le verrou de `migrate.js` (semaine 12).

- Sur une partie neuve, `node attacks/salon.js <code>` : les quatre lignes
  sont conformes.

- Dans le navigateur, avec quatre onglets : coupez le chat depuis
  l'animateur. Aucun joueur ne peut plus écrire, quelle que soit son
  instance.

## Jalon 4 : une instance s'arrête

1. Dans le navigateur, une partie avec trois joueurs, l'onglet Réseau
   ouvert (filtre WS). Lancez une question et répondez dans un onglet.
2. **Prédire.** Vous allez arrêter une des deux instances. Que verront les
   joueurs ? Le classement sera-t-il perdu ?
3. Arrêtez-la :

   ```bash
   docker stop deploy-api-2
   ```

4. Continuez la partie jusqu'au classement final.
5. Relancez l'instance : `docker compose up -d`.

**Expliquer.**

- Dans l'onglet Réseau (filtre WS), certains onglets ont ouvert une
  nouvelle connexion, d'autres non. Lesquels ?
- Qui a rétabli les connexions coupées, et vers quelle instance ?
- Pourquoi rien n'a-t-il été perdu ?

La note [Quand une instance tombe](/notes_de_cours/architecture/montee_en_charge#quand-une-instance-tombe)
donne les réponses.

**Pour aller plus loin.** Une troisième instance, sans toucher au fichier :

```bash
docker compose up -d --scale api=3
```

Il reste un état en mémoire dans l'API. Lequel, et que se passe-t-il si
son instance s'arrête ? Voir
[ce qui reste](/notes_de_cours/architecture/montee_en_charge#ce-qui-reste).

:::tip[À retenir]

Un service tourne en plusieurs instances s'il ne garde rien d'important en
mémoire. Les données vont dans la base. Les connexions restent attachées à
leur instance : l'adaptateur Redis relie les instances pour que
`io.to(...)` et `fetchSockets()` voient tout le salon. Une instance peut
alors s'arrêter sans que la partie s'arrête.

:::

## En panne ?

- `attacks/salon.js` répond `Ce pseudonyme est déjà pris. Créez une partie
  neuve.` : les robots de l'essai précédent sont inscrits dans cette
  partie.
- `attacks/salon.js` répond `ECONNREFUSED` : la prod de `deploy/` ne tourne
  pas (`docker compose ps`).
- Après le jalon 1, rien n'a changé : Caddy n'a pas relu son fichier
  (`docker compose restart caddy`).
- Un changement au code ne se voit pas : l'image n'a pas été reconstruite.
  `docker compose up -d` doit afficher `Recreated`, pas `Running`.
- `502` pendant quelques secondes après un `docker compose up -d` : les
  instances redémarrent.
- `getaddrinfo ENOTFOUND redis` dans `docker compose logs api` : le service
  `redis` manque dans `compose.yml`, ou porte un autre nom.
- `relation "chat_message" does not exist` : le fichier de la migration
  n'est pas dans `server/data/migrations/`, ou l'image a été construite
  avant.
- **Sans Docker (SQLite)** : cet exercice demande Docker. Le code des
  jalons 2 et 3 fonctionne quand même avec `npm run dev` et `npm test`.
