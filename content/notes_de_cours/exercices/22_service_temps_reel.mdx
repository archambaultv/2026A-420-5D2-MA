# Exercice 21 : le service temps réel

:::info

Ceci est un exercice formatif. Il n'y a rien à remettre. Il demande
**Docker Desktop**, démarré, et
l'[exercice 20](/notes_de_cours/exercices/deux_instances) terminé jusqu'au
jalon 3.

:::

L'API de Quiz M9 fait deux métiers : répondre à des requêtes HTTP, et tenir
des connexions Socket.IO ouvertes pendant toute une partie. On les sépare :
le temps réel devient un service à part, avec son propre nombre
d'instances.

L'adaptateur Redis de l'exercice 20 est ce qui rend la coupure possible :
les instances se parlent déjà par Redis. Il reste à décider qui tient les
connexions.

| Jalon | Ce que vous faites | Pourquoi |
|---|---|---|
| 1 | un service `realtime`, et Caddy lui envoie `/socket.io/*` | les connexions changent de service |
| 2 | l'API publie dans Redis au lieu d'être un serveur Socket.IO | l'API n'a plus aucune connexion |
| 3 | dimensionner à part, puis arrêter l'API | observer une panne partielle |

Note à garder ouverte :
[SaaS et microservices](/notes_de_cours/architecture/microservices).

Continuez sur votre branche `sem-13`. « Reconstruisez » a le même sens
qu'à l'exercice 20.

## Jalon 1 : le service `realtime`

- **Fichiers** : `server/src/realtime-server.js` (nouveau),
  `deploy/compose.yml`, `deploy/Caddyfile`
- **Note** : [Où couper Quiz M9](/notes_de_cours/architecture/microservices#où-couper-quiz-m9)

1. **Le point d'entrée.** Créez `server/src/realtime-server.js` : un
   serveur HTTP sans aucune route, auquel on greffe Socket.IO.

   ```js title="server/src/realtime-server.js"
   import { createServer } from 'node:http';
   import { attachRealtime } from './realtime.js';
   import { REDIS_URL } from './redis.js';

   if (!REDIS_URL) {
     throw new Error('REDIS_URL est obligatoire : sans Redis, ce service n’entend pas l’API.');
   }

   const port = process.env.PORT ?? 3000;
   // Socket.IO répond sur /socket.io ; tout le reste reçoit 404.
   const server = createServer((req, res) => {
     res.writeHead(404).end();
   });
   await attachRealtime(server);
   server.listen(port, () => {
     console.log(`Quiz M9 : service temps réel démarré sur le port ${port}`);
   });
   ```

2. **Le service.** Dans `deploy/compose.yml`, avant `client:` :

   ```yaml
     realtime:
       image: ghcr.io/${OWNER}/quizm9-api:${TAG:-latest}
       command: ["node", "src/realtime-server.js"]
       deploy:
         replicas: 2
       environment:
         NODE_ENV: production
         DATABASE_URL: postgres://quizm9:${POSTGRES_PASSWORD}@postgres:5432/quizm9
         REDIS_URL: redis://redis:6379
         SESSION_SECRET: ${SESSION_SECRET}
       depends_on:
         - api
         - redis
   ```

   C'est la **même image** que l'API. `command` remplace le `CMD` du
   `Dockerfile` : le conteneur lance l'autre point d'entrée.

   Dans le service `caddy`, ajoutez `- realtime` à `depends_on`.

3. **Le routage.** Dans `deploy/Caddyfile`, les connexions Socket.IO vont
   au nouveau service :

   ```caddy
   reverse_proxy /socket.io/* {
   	import instances realtime
   }
   ```

4. Reconstruisez, puis `docker compose restart caddy`.

**Vérifier.**

- `docker compose ps` : deux `api`, deux `realtime`.
- Sur une partie neuve, `node attacks/salon.js <code>` : les quatre lignes
  sont conformes.

**Expliquer.** Vous n'avez rien changé au code de l'API. Elle appelle
toujours `io.to(code).emit(...)` sur son propre serveur Socket.IO, auquel
plus aucun navigateur ne se connecte. Pourquoi les robots reçoivent-ils
quand même l'état ?

<details>
<summary>Réponse</summary>

Par l'adaptateur. `io.to(code).emit(...)` publie dans Redis, et les
instances `realtime`, abonnées, remettent le message à leurs connexions.
L'API n'a aucune connexion dans le salon, mais elle publie quand même.

De même, `fetchSockets()` interroge toutes les instances : l'API obtient
la présence en la demandant aux instances `realtime`.

</details>

## Jalon 2 : l'API publie

- **Fichiers** : `server/src/notify.js` (nouveau),
  `server/src/realtime.js`, `server/src/app.js`, `server/src/server.js`
- **Note** : [L'API publie, le temps réel écoute](/notes_de_cours/architecture/microservices#lapi-publie-le-temps-réel-écoute)

L'API démarre encore un serveur Socket.IO complet pour ne s'en servir que
comme porte-voix. On le remplace par un **émetteur**, qui ne sait que
publier.

1. **L'émetteur.** Créez `server/src/notify.js` :

   ```js title="server/src/notify.js"
   import { Emitter } from '@socket.io/redis-emitter';
   import { emitChatEnabled, onGameChanged } from './realtime.js';
   import { REDIS_URL, connectRedis } from './redis.js';

   const emitter = REDIS_URL ? new Emitter(await connectRedis()) : null;

   /** Une partie a changé (joueur inscrit, réponse reçue, question suivante…). */
   export async function gameChanged(code) {
     if (emitter) emitter.serverSideEmit('game:changed', code);
     else await onGameChanged(code);
   }

   /** L'animateur a coupé ou rouvert le chat de cette partie. */
   export function chatEnabledChanged(code, enabled) {
     if (emitter) emitter.to(code).emit('chat:enabled', enabled);
     else emitChatEnabled(code, enabled);
   }
   ```

   Les branches `else` servent sans Redis (`npm run dev`, les tests) : un
   seul processus, on appelle le temps réel directement.

2. **Le service écoute.** Dans `server/src/realtime.js` :

   - dans `attachRealtime`, après le bloc de l'adaptateur :

     ```js
     io.on('game:changed', (code) => onGameChanged(code).catch(console.error));
     ```

   - remplacez `broadcastChatEnabled` par les deux fonctions que
     `notify.js` importe :

     ```js
     export async function onGameChanged(code) {
       if (!io) return;
       io.local.to(code).emit('state', await stateWithPresence(code));
     }

     export function emitChatEnabled(code, enabled) {
       io?.to(code).emit('chat:enabled', enabled);
     }
     ```

   - `broadcastState` ne sert plus qu'ici (`'disconnect'`) : retirez son
     `export` et sa ligne `if (!io) return;`.

   - **coupez** la fonction `closeAtDeadline` : elle va dans l'API.

3. **L'API.** Dans `server/src/app.js` :

   - l'import de `./realtime.js` devient

     ```js
     import { chatEnabledChanged, gameChanged } from './notify.js';
     ```

   - collez `closeAtDeadline` avant les routes de la salle de jeu, sans
     `export`. Dedans, `broadcastState(code)` devient `gameChanged(code)` ;

   - les trois `await broadcastState(game.code)` des routes deviennent
     `await gameChanged(game.code)` ;

   - dans la route du chat, `broadcastChatEnabled` devient
     `chatEnabledChanged`.

4. **Plus de Socket.IO dans l'API.** Dans `server/src/server.js`, importez
   `REDIS_URL` de `./redis.js`, et la dernière ligne devient :

   ```js
   if (!REDIS_URL) await attachRealtime(server);
   ```

5. `npm test`, puis reconstruisez.

**Prédire.** Dans `onGameChanged`, on écrit `io.local.to(code)` et non
`io.to(code)`. Avec deux instances `realtime`, que recevrait chaque
navigateur avec `io.to(code)` ?

<details>
<summary>Réponse</summary>

L'état, deux fois. **Chaque** instance reçoit l'annonce `game:changed`, et
`io.to(code)` s'adresse à tout le salon, sur toutes les instances. Avec
`io.local`, chacune ne prévient que ses propres connexions.

Pour le voir : remplacez `io.local.to` par `io.to`, reconstruisez, et
relancez les robots. La ligne 1 affiche `2 2 2 2 2 2`. Remettez
`io.local`.

</details>

**Vérifier.**

- `npm test` passe, sans Redis : les tests tournent dans un seul
  processus.
- Sur une partie neuve, `node attacks/salon.js <code>` : les quatre lignes
  sont conformes.
- Dans le navigateur, une partie complète à quatre onglets, avec le chat
  coupé puis rouvert.

**Expliquer.** Les tests passent. Vérifient-ils que l'API et le service
temps réel se parlent ? Voir
[ce que ce découpage coûte](/notes_de_cours/architecture/microservices#ce-que-ce-découpage-coûte).

## Jalon 3 : dimensionner, puis tomber en panne

- **Note** : [La panne partielle](/notes_de_cours/architecture/microservices#la-panne-partielle)

1. **Dimensionner à part.** Une instance de l'API, trois du temps réel :

   ```bash
   docker compose up -d --scale api=1 --scale realtime=3
   docker compose ps
   ```

2. Dans le navigateur, une partie avec trois joueurs, dans le salon
   d'attente.

3. **Prédire.** Vous allez arrêter l'API. Pour chaque action, marchera-t-elle
   encore ?

   | Action | Passe par |
   |---|---|
   | écrire dans le chat | Socket.IO |
   | voir un joueur fermer son onglet | Socket.IO |
   | lancer la première question | HTTP |
   | ouvrir la page d'accueil | le client, qui appelle l'API |

4. Arrêtez l'API, puis essayez les quatre actions :

   ```bash
   docker compose stop api
   ```

5. Relancez-la, puis lancez la question :

   ```bash
   docker compose start api
   ```

**Expliquer.**

- Les connexions n'ont pas été coupées. Pourquoi ?
- « Question suivante » échoue après quelques secondes d'attente. D'où
  vient ce délai ? (Indice : `lb_try_duration`.)
- Refaites l'expérience dans l'autre sens, `docker compose stop realtime` :
  qu'est-ce qui marche encore ? Ouvrez
  `https://quizm9.localhost/api/games/<code>` dans un onglet.

**Discuter.** Ce service est-il un « vrai » microservice ? Relevez dans
`deploy/compose.yml` ce que `api` et `realtime` ont encore en commun.

<details>
<summary>Réponse</summary>

L'image, la base de données (`DATABASE_URL`) et le secret
(`SESSION_SECRET`). On les dimensionne séparément, mais on les déploie
ensemble, et un changement de schéma touche les deux. C'est un compromis
courant, à connaître comme tel.

</details>

:::tip[À retenir]

Couper un service, c'est décider qui tient quoi : ici, l'API garde les
routes et la base, le service temps réel garde les connexions. Ils ne
s'appellent pas : l'API publie, le service écoute. Chacun a son nombre
d'instances, et l'un peut tomber sans entraîner l'autre.

:::

## En panne ?

- `REDIS_URL est obligatoire` dans `docker compose logs realtime` : la
  variable manque dans le service `realtime`.
- Après le jalon 1, les robots ne reçoivent rien : Caddy n'a pas relu son
  fichier (`docker compose restart caddy`), ou `import instances realtime`
  ne correspond pas au nom du service.
- `Jeton invalide.` à la connexion d'un joueur : `SESSION_SECRET` manque
  dans le service `realtime`, ou n'est pas celui de l'API.
- `does not provide an export named …` au démarrage : un nom importé par
  `notify.js` ou `app.js` ne correspond pas à ce que `realtime.js` exporte.
- Après le jalon 2, plus aucun état n'arrive : la ligne
  `io.on('game:changed', …)` manque, ou le nom de l'événement diffère
  entre `notify.js` et `realtime.js`.
- Avec `npm run dev`, le jeu ne se met plus à jour : `REDIS_URL` est
  définie dans `server/.env`. Retirez-la : en développement, un seul
  processus fait tout.

## Nettoyer

Dans `deploy/` :

```bash
docker compose down -v
docker image rm ghcr.io/archambaultv/quizm9-api:s13 ghcr.io/archambaultv/quizm9-client:s13
```
