# Exercice 17 : un seul gagnant

:::info

Ceci est un exercice formatif. Il n'y a rien à remettre.

:::

Cet exercice corrige quatre bogues de concurrence, un par jalon.

Note à garder ouverte : [Lire, vérifier, écrire](/notes_de_cours/concurrence/lire_verifier_ecrire).

## Les tests sont fournis

Le fichier `server/test/concurrence.test.js` contient 16 tests, qui échouent
au départ. Chaque jalon en fait passer quelques-uns :

```bash
npm run test:concurrence -w server
```

| Après le jalon | Tests qui passent | Total |
|---|---|---|
| 0 | aucun | 0 / 16 |
| 1 | J1.1 à J1.4 | 4 / 16 |
| 2 | J2.1 à J2.4 | 8 / 16 |
| 3 | J3.1 à J3.5 | 13 / 16 |
| 4 | J4.1 à J4.3 | 16 / 16 |

Chaque étape ci-dessous dit quel test elle fait passer. Si un test reste
rouge, lisez-le : son code est la spécification.

## Jalon 0 : la tempête

Le point de départ est la solution de la semaine 10.

```bash
git checkout main
git pull
git checkout -b sem-11
npm install
docker compose up -d postgres   # sans Docker : DATABASE_URL=sqlite:data/quizm9.db dans server/.env
npm run dev
```

1. Connectez-vous (`alice` / `alice`) et créez une partie sur « Révision
   express ». **Ne la lancez pas.**
2. Dans un autre terminal :

   ```bash
   node attacks/tempete.js CODE
   ```

   Douze robots rejoignent la partie. À la première question, chacun répond
   deux fois en même temps, puis tous reviennent à l'échéance.
3. Lancez la question et attendez la fin des 20 secondes.


## Jalon 1 : une réponse par joueur

- **Fichiers** : `server/data/schema.sql`, `server/data/schema.sqlite.sql`,
  `server/src/repository/games.js`, `server/src/app.js`

1. **La contrainte.** Dans `server/data/schema.sql` et
   `server/data/schema.sqlite.sql`, à la fin, remplacez le commentaire sur
   `(game_id, player_id, question_id)` par :

   ```sql
   CREATE UNIQUE INDEX IF NOT EXISTS answer_once ON answer (game_id, player_id, question_id);
   ```

   ✔ **J1.1**

2. **Un doublon n'est pas une erreur.** Dans
   `server/src/repository/games.js`, fonction `recordAnswer`, ajoutez
   `ON CONFLICT DO NOTHING` avant `RETURNING id`. Sans ligne insérée, `rows`
   est vide : retournez `rows[0]?.id ?? null`. Mettez la JSDoc à jour
   (`number|null`).

   ✔ **J1.2**

3. **La route.** Dans `server/src/app.js`, route
   `POST /api/games/:code/answers` :
   - supprimez la vérification `findAnswer` : c'est la base qui tranche
     maintenant ;
   - gardez l'id retourné par `recordAnswer`. S'il vaut `null`, répondez
     `409` avec `{ error: 'Ce joueur a déjà répondu.' }`.

   ✔ **J1.3**, **J1.4**

**Vérifier.** Redémarrez le serveur. S'il refuse de démarrer, la tempête a
laissé des doublons dans votre base : voir [En panne ?](#en-panne-). Relancez
la tempête sur une nouvelle partie : 12 réponses pour 12 robots.

## Jalon 2 : une seule clôture

- **Fichiers** : `server/src/repository/games.js`,
  `server/src/repository/index.js`, `server/src/game.js`

1. **La transition conditionnelle.** Dans `server/src/repository/games.js`,
   écrivez :

   ```js
   /**
    * Fait passer la partie de l'état `from` à l'état `to`, SEULEMENT si elle
    * est encore dans l'état `from`.
    *   from : { state, questionIndex }
    *   to   : { state, questionIndex, questionStartedAt }
    * @returns {Promise<boolean>} true si la partie a changé
    */
   export async function transitionGame(gameId, from, to, db = pool) {
     const { rowCount } = await db.query(
       `UPDATE game SET state = $1, question_index = $2, question_started_at = $3
         WHERE id = $4 AND …`,
       [to.state, to.questionIndex, to.questionStartedAt, gameId, from.state, from.questionIndex],
     );
     // …
   }
   ```

   Complétez le `WHERE` et la valeur de retour. Exportez-la dans
   `server/src/repository/index.js`.

   ✔ **J2.1**

2. **Lire dans la transaction.** Dans `server/src/repository/games.js`,
   ajoutez le paramètre `db = pool` à `getAnswersForQuestion`, comme celui de
   `setAnswerPoints`.

3. **`closeQuestion` ne gagne qu'une fois.** Dans `server/src/game.js`,
   fonction `closeQuestion` :
   - au début de la transaction, **avant** de lire les réponses : la
     transition de `{ state: 'question', questionIndex: game.question_index }`
     vers `results` (même index, `questionStartedAt: null`), avec `tx` ;
   - si elle échoue, `return false` : une autre requête a clos la question ;
   - puis lisez les réponses avec `tx` (déplacez la lecture dans la
     transaction). La boucle des points ne change pas ;
   - supprimez l'appel à `updateGameState`, remplacé par la transition ;
   - `closeQuestion` retourne `true` si c'est elle qui a clos, `false`
     sinon (y compris au tout début, si `game.state !== 'question'`).

   ✔ **J2.2**, **J2.3**, **J2.4**

**Vérifier.** La tempête : plus aucun score au-dessus de 10.

## Jalon 3 : le double-clic de l'animateur

- **Fichiers** : `server/src/app.js`, `server/src/game.js`,
  `client/app/api.js`, `client/app/routes/lobby.jsx`,
  `client/app/routes/game.jsx`

**Observer.** Jouez jusqu'au classement d'une question, puis double-cliquez
sur « Question suivante » : la question suivante s'affiche et se clôt aussitôt.

1. **L'état attendu.** Dans `server/src/app.js`, au début de la route
   `POST /api/games/:code/next`, lisez le corps : `const expected = req.body ?? {}` (pas `state`, ce nom est déjà
   pris plus bas). Si `expected.state` n'est pas une chaîne ou si
   `expected.questionIndex` n'est pas un entier (`Number.isInteger`),
   répondez `400`.

   ✔ **J3.1**

2. Dans la même route, après `closeQuestionIfExpired`, si `expected` ne
   correspond pas à
   `game.state` et `game.question_index`, répondez `409` avec
   `{ error: 'La partie a déjà avancé.' }`.

   ✔ **J3.2**, **J3.3**

3. **`advance` ne gagne qu'une fois.** Dans `server/src/game.js`, fonction
   `advance`, remplacez les deux `updateGameState` par un seul
   `transitionGame`, de l'état lu
   (`game.state`, `game.question_index`) vers la question suivante ou vers
   `finished`. `advance` retourne le résultat de la transition (et `false`
   si la partie est déjà terminée).

   Dans `server/src/app.js`, route `next`, gardez le résultat de
   `closeQuestion` ou d'`advance` : s'il vaut `false`, répondez `409`.

   ✔ **J3.4**, **J3.5**

4. **Le client.** Dans `client/app/api.js`,
   `nextQuestion(code, { state, questionIndex })` envoie ce corps. Dans
   `client/app/routes/lobby.jsx` et `client/app/routes/game.jsx`, passez
   `game` à `nextQuestion`. Dans `client/app/routes/game.jsx`, ajoutez un état
   `advancing` : vrai pendant l'envoi, il désactive les boutons de
   l'animateur.

**Vérifier.** Le double-clic : la question reste ouverte. Onglet Réseau :
un `200`, puis un `409`, ou un seul appel si le bouton était déjà désactivé.

## Jalon 4 : la réponse pendant la clôture

- **Fichiers** : `server/src/repository/games.js`, `server/src/app.js`

La route vérifie `game.state === 'question'`, puis fait d'autres lectures
avant d'insérer. Une clôture peut passer entre les deux : la réponse est
insérée trop tard, et elle n'aura jamais de points.

1. **La route d'abord.** Dans `server/src/app.js`, route
   `POST /api/games/:code/answers`, passez `game.question_index` en sixième
   argument de `recordAnswer` (ignoré pour l'instant). Le `409` couvre maintenant
   deux cas : `{ error: 'Déjà répondu, ou la question est close.' }`.

2. Dans `server/src/repository/games.js`, `recordAnswer` reçoit ce sixième
   paramètre, `questionIndex`, et n'insère que si la partie est encore sur
   cette question :

   ```sql
   INSERT INTO answer (game_id, player_id, question_id, choice_id, answered_at)
   SELECT $1, $2, $3, $4, $5
    WHERE EXISTS (
      SELECT 1 FROM game
       WHERE id = $1 AND state = 'question' AND question_index = $6
         FOR SHARE
    )
   ON CONFLICT DO NOTHING
   RETURNING id
   ```

   Lisez [pourquoi `FOR SHARE`](/notes_de_cours/concurrence/lire_verifier_ecrire#4-linsert-conditionnel-et-for-share)
   avant de l'écrire.

   ✔ **J4.1**, **J4.2**, **J4.3**

**Vérifier.**

```bash
npm test
```

`fail 0` : les 16 tests de concurrence, et tous les anciens.

## Pour aller plus loin

- **Le même pseudonyme, deux fois.** Dans `server/src/app.js`, la route
  `POST /api/games/:code/players` vérifie
  `findPlayer`, puis insère. Deux joueurs qui choisissent `zoé` en même temps :
  la contrainte `UNIQUE (game_id, nickname)` existe déjà, mais la deuxième
  requête reçoit une erreur 500. Corrigez-la en 409, et écrivez le test.
- **Rejoindre pendant le lancement.** Même route : `game.state !== 'lobby'`,
  puis l'insertion. Rendez l'insertion conditionnelle, comme au jalon 4.
- **Pourquoi pas le chat ?** Dans `server/src/realtime.js`, `nextMessageId++` lit, puis
  écrit une variable partagée par toutes les connexions. Pourquoi deux
  messages simultanés ne reçoivent-ils jamais le même id ?
- **Pour le projet 2.** Écrivez le test « deux coups joués en même temps sur
  la même position : un seul est accepté », puis faites-le passer.

La solution (branche `sol-11`) a un commit par jalon, plus la démonstration
de l'horloge du client faite en classe.

## En panne ?

- **Le serveur refuse de démarrer** : `could not create unique index
  "answer_once"` (PostgreSQL) ou `UNIQUE constraint failed` (SQLite). La
  tempête du jalon 0 a laissé des doublons. Remettez la base à zéro :
  `docker compose down -v`, puis `docker compose up -d postgres`. Sans
  Docker : supprimez `server/data/quizm9.db`.
- `ECONNREFUSED 127.0.0.1:5432` dans les tests : PostgreSQL ne tourne pas,
  `docker compose up -d postgres`.
- `repository.transitionGame is not a function` : elle n'est pas exportée
  dans `repository/index.js`.
- **J2.2 ou J2.3 compte encore les points en double** : la transition n'est
  pas la première requête de la transaction, ou elle reçoit le pool au lieu
  de `tx`.
- `Identifier 'state' has already been declared` : dans la route `next`,
  nommez le corps `expected`.
- **J3.1 à J3.3 passent, mais pas J3.5** : la route compare bien l'état
  attendu, mais `advance` écrit encore sans condition.
- **J4.3 échoue sous PostgreSQL, mais passe sous SQLite** : il manque
  `FOR SHARE`.
- **Un test de course passe avant sa correction** : ça peut arriver (la
  course ne se produit pas à chaque exécution). Les tests rejoués pas à pas
  (J2.2, J3.4, J4.1) échouent, eux, à coup sûr.
