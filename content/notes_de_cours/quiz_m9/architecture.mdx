# L'architecture de Quiz M9

Tout le cours s'appuie sur **Quiz M9**, un jeu-questionnaire en direct : un
animateur crée une partie et obtient un **code** ; les joueurs rejoignent avec
ce code et un pseudonyme, sans compte ; les questions défilent, le classement
monte.

**Cette page décrit le dépôt
[github.com/archambaultv/2026A-420-5D2-MA-QuizM9](https://github.com/archambaultv/2026A-420-5D2-MA-QuizM9)
dans sa version courante** : elle est mise à jour chaque fois que
l'architecture change. Gardez-la ouverte pendant que vous travaillez dedans.

*Dernière mise à jour : semaine 3.*

## Deux processus

`npm run dev` démarre **deux serveurs** :

```
┌──────────────────────────────┐        ┌──────────────────────────────┐
│  client : port 5173          │        │  serveur : port 3000         │
│  React Router mode framework │  /api  │  Express                     │
│  rend les sept pages         │ ─────► │  route → moteur → repository │
│  (HTML + React)              │        │            │                 │
└──────────────────────────────┘        │            ▼                 │
        ▲                               │  data/quizm9.db (SQLite)     │
        │ http://localhost:5173         └──────────────────────────────┘
     navigateur
```

- Le **serveur** (`server/`) ne parle que JSON : c'est l'API. Toutes les
  données vivent chez lui, dans `quizm9.db` (ou au chemin donné par la
  variable d'environnement `DB_PATH`).
- Le **client** (`client/`) rend les pages. Quand une page a besoin de
  données, elles viennent **toujours** de l'API, jamais d'un accès direct à
  la base.
- En développement, les appels `fetch('/api/…')` du navigateur sont relayés
  par Vite au port 3000 (voir `client/vite.config.js`). Les `loader` et
  `action`, eux, tournent sur le serveur du client et appellent l'API par
  son adresse complète, `API_URL` (`client/app/api-url.js`).

Le client tourne en **React Router mode framework**. C'est toujours du React
(composants, props, `useState`, `useEffect`), mais chaque page a une
**URL**.

## Comment jouer en développement

Ouvrez **deux navigateurs** (ou une fenêtre normale et une fenêtre privée) :
l'animateur dans l'une, un joueur dans l'autre. Vous pouvez ajouter un deuxième
joueur en ouvrant une autre fenêtre privée.

## Les sept pages

L'application Quiz M9 a sept pages. Le dossier `client/app/routes/`
contient un fichier par page.

| Page | URL | Fichier |
|---|---|---|
| Accueil | `/` | `home.jsx` |
| Catalogue public | `/catalogue` | `catalogue.jsx` |
| Liste d'animateur | `/quizzes` | `quizzes.jsx` |
| Un questionnaire | `/quizzes/:id` | `quiz-details.jsx` |
| Éditeur | `/quizzes/:id/edit` | `quiz-edit.jsx` |
| Salon d'attente | `/salon/:code` | `lobby.jsx` |
| Salle de jeu | `/jeu/:code` | `game.jsx` |

Le scénario d'une partie : l'animateur choisit un questionnaire dans le
**catalogue** → tout le monde se retrouve au **salon** avec le code → la
partie se joue dans la **salle de jeu**.

L'espace auteur (liste, questionnaire, éditeur) est rendu **côté serveur** :
ses pages lisent par un `loader` et écrivent par une `action` (semaine 3).
Le catalogue reste rendu côté client, comme témoin.

## Se repérer dans le dépôt

Voici la structure du dépôt, avec les fichiers les plus importants.

```
compose.yml              Quiz M9 d'une seule commande : docker compose up
server/
  Dockerfile             l'image de l'API
  src/server.js          les routes de l'API
  src/game.js            le moteur de jeu (états, échéances, pointage)
  src/scoring.js         calculateScore, la fonction pure de pointage
  src/repository/        TOUT le SQL
  data/schema.sql        les sept tables, fourni au complet
  data/seed.sql          les questionnaires de démonstration
  data/quizm9.db         votre base locale (non versionnée)
  verifier/              le harnais npm run verifier qui sert de tests unitaires
client/
  Dockerfile             l'image du client, en deux étapes
  server.js              le serveur de production du client (relais /api + pages)
  app/routes.js          une ligne par page
  app/routes/            les sept pages
  app/api.js             les appels fetch vers l'API, depuis le navigateur
  app/api-url.js         l'adresse de l'API, vue des loader et action
  app/useGame.js         le sondage toutes les secondes
```

## Le chemin d'une requête

Voici le parcours d'une requête, de l'interface du joueur jusqu'à la base de données :

```
navigateur
   │  POST /api/games/747311/answers   { nickname, choiceId }
   ▼
route (server.js)          reçoit la requête, valide, répond en JSON
   │
   ▼
moteur de jeu (game.js)    les règles : états, échéances, pointage
   │
   ▼
repository/ (index.js)     TOUT le SQL, et rien d'autre que le SQL
   │
   ▼
quizm9.db (SQLite)         la base de données
```

Chaque étage ne connaît que celui du dessous. La route ne fait pas de SQL ;
le repository n'applique pas de règles de jeu ; le moteur ne lit jamais
`req` ni n'écrit `res`.

Suivons une première requête, `POST /api/games/:code/answers`, envoyée
quand un joueur répond :

1. **La route** (`server.js`) retrouve la partie
   (`repository.findGameByCode`), vérifie qu'une question est en cours, que
   le joueur existe, qu'il n'a pas déjà répondu, que le choix est valide.
   Sinon : `400` et un message.
2. Elle enregistre la réponse : `repository.recordAnswer(game.id, player.id,
   question.id, choiceId, Date.now())`. L'horodatage est pris **ici**, sur
   le serveur.
3. **Le repository** exécute l'`INSERT INTO answer …` et retourne l'id.
4. La ligne est dans le fichier `quizm9.db`. Le serveur peut redémarrer :
   elle y sera encore.

Suivons une deuxième requête, `POST /api/games/:code/next`, envoyée quand
l'animateur clôt la question en cours :

1. **La route** (`server.js`) retrouve la partie ; elle est en état
   `question`, la route demande donc au moteur de la clore
   (`closeQuestion`).
2. **Le moteur** (`game.js`) relit toutes les réponses reçues
   (`repository.getAnswersForQuestion`) et calcule les points de chacune
   avec `calculateScore`, la fonction pure de `scoring.js`. Il déclenche
   ensuite **trois écritures qui doivent réussir ensemble** : les points de
   chaque réponse (`setAnswerPoints`), les totaux des joueurs
   (`addPointsToPlayer`) et l'état de la partie (`updateGameState`).
3. **Le repository** exécute le SQL de chaque appel, et rien d'autre : pas
   de règles de jeu, pas de calcul de points. C'est aussi lui qui fournit la
   **transaction**. Le moteur groupe ses trois appels dans
   `repository.withTransaction(...)`, dont le `BEGIN`, le `COMMIT` et le
   `ROLLBACK` sont écrits dans `repository/db.js` : tout passe, ou rien.
4. La route répond l'état public de la partie : les joueurs voient les
   résultats et le classement à jour.


Suivons enfin une écriture depuis un formulaire, l'auteur qui crée un
questionnaire sur `/quizzes` :

1. Le `<Form method="post">` envoie le titre à l'**`action`** de la route,
   qui s'exécute sur le serveur du client (5173).
2. L'`action` appelle `POST /api/quizzes` sur Express (3000), à l'adresse
   `API_URL`.
3. **La route** valide le titre (400 s'il est vide), puis
   `repository.createQuiz(title)` fait l'`INSERT`.
4. L'`action` reçoit l'id et répond `redirect('/quizzes/4/edit')` : le
   navigateur arrive sur l'éditeur, dont le `loader` relit le questionnaire.

## Avec Docker

`docker compose up --build` démarre les deux processus dans deux
conteneurs, sur un réseau privé où le client joint l'API par son nom
(`API_URL=http://api:3000`). La base vit dans le volume `quizm9-data`,
monté sur `/data` dans le conteneur de l'API (`DB_PATH=/data/quizm9.db`) :
elle survit à la destruction des conteneurs. En production, le client est
construit puis servi par `client/server.js`, qui relaie `/api` comme Vite
le fait en développement.

## Le temps réel de la partie

Pour l'instant la partie ne se joue pas en temps réel : le navigateur interroge
l'état de la partie **toutes les secondes** en HTTP (`useGame.js`,
`setInterval` + `fetch`), même quand il ne se passe rien. C'est un choix assumé
de la semaine 1. Une meilleure solution sera implantée à la semaine 7.
