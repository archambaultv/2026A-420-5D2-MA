# La partie survit au redémarrage

Le prototype de la semaine 1 a un défaut fatal : on arrête le serveur, tout
disparaît — parties, joueurs, pointages, questionnaires. Ce bloc le corrige en
déplaçant l'état de la mémoire vers **SQLite**. Aucun serveur de base de
données à installer : un fichier, et `node:sqlite`.

## Le schéma de Quiz M9

Sept tables, qui serviront jusqu'à la fin de la session :

```
account ──< quiz ──< question ──< choice
             │
             └──< game ──< player ──< answer >── question
```

| Table | Rôle | À remarquer |
|---|---|---|
| `account` | les auteurs (comptes, semaine 5) | vide pour l'instant |
| `quiz` | un questionnaire publié | appartiendra à un `account` |
| `question` | une question, son ordre, sa durée | `position` la place dans le questionnaire |
| `choice` | une réponse possible | `is_correct` : 0 ou 1 |
| `game` | une partie en cours ou passée | le `code`, l'index de la question courante, l'état |
| `player` | un pseudonyme dans une partie | pas un compte : il n'existe que dans sa partie |
| `answer` | un choix d'un joueur à une question | porte un **horodatage du serveur** |

Deux décisions à retenir, parce qu'elles reviendront :

- `answer` garde le **moment du serveur**, jamais celui du client — le bonus
  de rapidité en dépend (semaine 11) ;
- `(game, player, question)` deviendra une contrainte d'**unicité** : un
  joueur ne répond qu'une fois, et c'est le schéma qui l'imposera, pas le
  code (semaine 11 encore).

## Écrire avec node:sqlite

La semaine 1 lisait ; cette semaine on écrit.

On ouvre la base et on crée les tables au démarrage (idempotent grâce à
`IF NOT EXISTS`) :

```js
import { DatabaseSync } from 'node:sqlite';
const db = new DatabaseSync('data/quiz.db');

db.exec(`CREATE TABLE IF NOT EXISTS player (…);`);
```

**Insérer.** Les `?` sont des paramètres : la valeur est passée à part, JAMAIS
collée dans la chaîne SQL.

```js
const gameId = 7;           // normalement : req.params
const nickname = 'Alice';   // normalement : req.body

const resultat = db
  .prepare('INSERT INTO player (game_id, nickname) VALUES (?, ?)')
  .run(gameId, nickname);
const playerId = resultat.lastInsertRowid;   // l'id attribué par SQLite
```

**Mettre à jour.** Même mécanique, avec un `WHERE` :

```js
const gameId = 7;           // normalement : req.params
const questionIndex = 2;    // normalement : calculé par le serveur

db.prepare('UPDATE game SET question_index = ? WHERE id = ?')
  .run(questionIndex, gameId);
```

Plusieurs écritures qui doivent réussir **ensemble** — clore une question et
inscrire les pointages, par exemple — s'enveloppent dans une transaction :

```js
db.exec('BEGIN');
try {
  // … les écritures …
  db.exec('COMMIT');
} catch (e) {
  db.exec('ROLLBACK');
  throw e;
}
```

## La règle du bloc : tout le SQL derrière `repository/`

À partir de cette semaine, **aucune requête SQL en dehors d'un module
`repository/`** (le patron *repository* — « dépôt » en français). Les routes
appellent des fonctions nommées ; le SQL vit derrière.

```js
// repository/games.js
export function addPlayer(gameId, nickname) { /* le SQL est ICI */ }

// server.js — la route ne connaît plus le SQL
import { addPlayer } from './repository/games.js';
```

Ce n'est pas de l'esthétique. La semaine 4, on changera SQLite pour
PostgreSQL : si tout le SQL est derrière `repository/`, le changement tient en
quelques lignes. Si le SQL est éparpillé dans les routes, c'est une réécriture.

## Ce qui reste volontairement rustique

Les questionnaires s'écrivent encore **en SQL, à la main** — l'interface
d'édition arrive la semaine 3. Et le client sonde toujours toutes les secondes.
