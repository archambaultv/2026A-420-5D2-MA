# Les secrets

Quiz M9 a des secrets : le `GITHUB_CLIENT_SECRET` de l'application OAuth, et
le `SESSION_SECRET` qui signe les cookies de session. Un secret, c'est une
valeur qui donne un pouvoir à qui la connaît. La question de la semaine 6 :
**où vivent-ils, et où ne doivent-ils jamais aller ?**

## La règle : jamais dans le dépôt

> **Un secret ne va jamais dans le code, donc jamais dans le dépôt Git.**

Le dépôt se clone, se pousse, se rend public un jour. Un secret écrit dans un
fichier suivi par Git y reste dans **l'historique**, même effacé plus tard :
il suffit de remonter un commit. Un secret qui a touché un dépôt est un
secret grillé, à changer.

Dans Quiz M9, les secrets vivent dans `server/.env`, qui est dans
`.gitignore` :

```
# Les secrets : jamais dans le dépôt. Voir server/.env.example.
.env
```

Ce qui est versionné, c'est `server/.env.example` : le **modèle**, avec les
noms des variables et des valeurs vides. Chacun copie le modèle en `.env` et
le remplit avec ses propres valeurs. Le code lit les valeurs dans
l'environnement, il ne les contient pas :

```js
const SECRET = process.env.SESSION_SECRET;
```

Vérifiez toujours avec `git status` que `.env` **n'apparaît pas** avant de
commiter.

## La valeur par défaut est un piège

Jusqu'à la semaine 5, `session.js` avait un filet :

```js title="server/src/session.js (version vulnérable)"
const SECRET = process.env.SESSION_SECRET ?? 'developpement-seulement';
```

Pratique : l'application démarre même sans `.env`. Et dangereux : cette
valeur par défaut est **dans le dépôt**, donc publique. Quiconque lit le
code connaît la clé qui signe les cookies. Or c'est cette clé, et elle
seule, qui empêche de fabriquer un cookie de session valide (voir [La
session](/notes_de_cours/auth/session), « Signer, pas chiffrer »). Si un
déploiement oublie de définir `SESSION_SECRET`, il tourne avec la clé
publique, et **n'importe qui peut se forger la session de son choix**, y
compris celle d'un administrateur.

Le piège d'une valeur par défaut, c'est qu'elle **cache l'oubli** : tout a
l'air de marcher. Une configuration manquante doit faire **échouer bruyamment**,
pas continuer en silence avec une valeur dangereuse.

## La correction : pas de défaut, une clé exigée

```js title="server/src/session.js (corrigé)"
const SECRET = process.env.SESSION_SECRET;
// Pas de valeur par défaut : elle serait dans le dépôt, donc publique, et
// quiconque la lit fabrique la session de son choix. Sans clé, ou avec une
// clé trop courte pour résister à qui essaie toutes les possibilités, le
// serveur refuse de démarrer.
if (!SECRET || SECRET.length < 32) {
  throw new Error('SESSION_SECRET absente ou trop courte (32 caractères au moins) : voir server/.env.example.');
}
```

Deux choses :

- **Aucun défaut.** Sans `SESSION_SECRET`, le serveur ne démarre pas. L'oubli
  se voit tout de suite, au lancement, pas trois semaines plus tard en
  production.
- **Une longueur minimale.** Une clé courte se retrouve en essayant toutes
  les possibilités. 32 caractères aléatoires, c'est hors de portée. Node en
  produit une :

  ```bash
  node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
  ```

Le modèle `server/.env.example` le rappelle, et laisse la valeur vide pour
forcer chacun à mettre la sienne.

## En production, l'environnement plutôt qu'un fichier

En développement, `.env` est commode. En production, le fichier `deploy/.env`
n'est toujours pas dans le dépôt, et `docker compose` injecte ces valeurs
dans le conteneur comme variables d'environnement :

```yaml title="deploy/compose.yml"
environment:
  SESSION_SECRET: ${SESSION_SECRET}
  GITHUB_CLIENT_SECRET: ${GITHUB_CLIENT_SECRET}
```

Le code lit toujours `process.env`, qu'il tourne sur votre poste ou dans un
conteneur. La source change, la règle ne change pas : **le secret vit dans
l'environnement de la machine, jamais dans le code.**

## Un secret grillé se change

Un secret qui a fuité, poussé dans un dépôt public ou collé dans un canal de
discussion, ne se « dé-fuite » pas. La seule réponse est de le **remplacer**
et de révoquer l'ancien :

- `GITHUB_CLIENT_SECRET` : *Generate a new client secret* sur la page de
  l'application OAuth, puis supprimer l'ancien.
- `SESSION_SECRET` : en générer un nouveau. Effet de bord attendu, et sain :
  tous les cookies signés avec l'ancien deviennent invalides, donc toutes
  les sessions en cours sont fermées.
