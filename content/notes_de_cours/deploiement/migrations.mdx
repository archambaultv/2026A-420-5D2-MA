# Les migrations

## Le problème

Jusqu'ici, le serveur rejouait `schema.sql` à chaque démarrage :

```sql
CREATE TABLE IF NOT EXISTS player (
  id       INTEGER PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
  game_id  INTEGER NOT NULL REFERENCES game(id),
  nickname TEXT NOT NULL,
  emoji    TEXT NOT NULL DEFAULT '🙂',   -- la colonne qu'on vient d'ajouter
  score    INTEGER NOT NULL DEFAULT 0
);
```

`IF NOT EXISTS` veut dire : « si la table existe, ne fais **rien** ». Sur
une base neuve, la table est créée avec la colonne `emoji`. Sur une base
qui existe déjà, la table est laissée telle quelle, **sans** la colonne. Le
premier `INSERT` qui la nomme échoue :

```
column "emoji" of relation "player" does not exist
```

Les tests, eux, passent : chaque fichier de test crée une base neuve.

C'est exactement la situation d'un déploiement. La base de production
contient les parties et les comptes des utilisateurs ; on ne peut pas la
jeter pour la recréer. Il faut la **faire évoluer**.

## Les migrations numérotées

Une **migration** est un fichier SQL qui fait passer la base d'une version
du schéma à la suivante. On les numérote, et on les applique dans l'ordre :

```
server/data/migrations/
  001_schema_initial.sql     ← les tables de la semaine 11
  002_animal_du_joueur.sql   ← ALTER TABLE player ADD COLUMN emoji …
```

La base retient celles qu'elle a déjà reçues, dans une table :

```sql
SELECT * FROM schema_migration;
--            name           |  applied_at
-- --------------------------+---------------
--  001_schema_initial.sql   | 1763485200000
--  002_animal_du_joueur.sql | 1763485200004
```

Cette table n'est pas fournie par PostgreSQL et n'est dans aucune
migration : c'est `migrate.js` qui la crée. Au démarrage, l'API
(`server/src/repository/migrate.js`) :

1. lit la liste des fichiers du dossier, triés par nom ;
2. crée la table `schema_migration` si elle n'existe pas, puis la lit ;
3. applique chaque fichier qui n'y est pas encore, puis l'y ajoute.

Chaque base reçoit donc exactement ce qui lui manque :

| La base | Au démarrage |
|---|---|
| neuve | 001, puis 002 |
| créée par `schema.sql`, avant les migrations | 001 (sans effet, grâce aux `IF NOT EXISTS`), puis 002 |
| déjà migrée | rien |

## Ajouter une colonne sans rien perdre

```sql title="002_animal_du_joueur.sql"
ALTER TABLE player ADD COLUMN IF NOT EXISTS emoji TEXT NOT NULL DEFAULT '🙂';
```

- `ALTER TABLE … ADD COLUMN` modifie la table en place : les lignes
  existantes restent.
- `NOT NULL` exige une valeur dans **chaque** ligne, y compris les
  anciennes. Sans `DEFAULT`, PostgreSQL refuse la migration sur une table
  qui contient déjà des joueurs. Avec `DEFAULT '🙂'`, les anciens joueurs
  reçoivent cette valeur.
- `IF NOT EXISTS` : une base créée par un `schema.sql` qui contenait déjà
  la colonne l'a déjà. Sans lui, la migration échouerait sur cette base.

## Les règles

- **Une migration appliquée ne se modifie plus.** La base de production
  l'a déjà reçue et ne la relira jamais. Pour corriger, on écrit la
  migration suivante.
- **Toutes les migrations se font dans une transaction.** Si l'une échoue,
  aucune n'est appliquée, et le serveur ne démarre pas. PostgreSQL permet
  de défaire un `CREATE TABLE` ou un `ALTER TABLE` par un `ROLLBACK`.
- **Une sauvegarde avant de migrer en production.** Une migration qui
  supprime une colonne supprime ses données :

  ```bash
  docker compose exec postgres pg_dump -U quizm9 quizm9 > sauvegarde.sql
  ```

- **Deux instances qui démarrent en même temps** ne doivent pas appliquer
  la même migration deux fois. `migrate.js` prend d'abord un verrou
  (`pg_advisory_xact_lock`) : la deuxième attend, puis trouve tout appliqué.

En entreprise, un outil s'en charge (Flyway, Liquibase, Prisma Migrate,
node-pg-migrate). Ils suivent tous ce principe : des fichiers numérotés,
et une table qui retient ce qui a été appliqué.

:::tip[À retenir]

`CREATE TABLE IF NOT EXISTS` crée une table, il ne la modifie jamais. Un
changement de schéma sur une base qui contient des données s'écrit comme
une migration numérotée, appliquée une seule fois, dans l'ordre, et retenue
par la base elle-même.

:::
